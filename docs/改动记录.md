## 一、USB 升级功能改动

### 1.1 文件: app_src/system_config/app_config.h

**改动 A — 关闭 HS USB 在线调音 HID(保留 FS):**

位置: L159

```c
//#define CFG_COMMUNICATION_BY_HS_USB    //在线调音硬件接口HS USB HID
```

- 原为 `#define CFG_COMMUNICATION_BY_HS_USB`,现注释掉,关闭 HS 在线调音 HID。
- 保留 L160 `#define CFG_COMMUNICATION_BY_FS_USB`(FS USB 在线调音 HID)。

**改动 B — 强制 Device 走 FS 端口(A8/A9):**

位置: L712

```c
#define OTG_DEVICE_PORT_FS
```

- B2688A2 定义了 `CHIP_PIN_HSOTG`,若无此宏,`OTG_DEVICE_PORT_FS` 默认不生效,Device 会按 HS 枚举。
- 强制定义后,FS 设备检测/枚举走 A8/A9(与硬件接线一致)。

### 1.2 硬件根因(已解决)

- **问题现象**: 插入 USB 后设备管理器无任何枚举迹象,设备表现为停止工作/串口无日志。
- **最终根因**: USB 连接器的 **GND 误接到了 3.3V**(VCC 5V 正常)。重新正确连接 GND 后,USB 直连升级恢复正常。
- **经验**: 排查 USB 枚举失败时,除软件/宏配置外,必须优先核实 VCC/GND/DP/DM 实际接线。

### 1.3 引脚确认结论

- **FS USB(全速)**: D+(DP)=PA9, D-(DM)=PA8,与 GPIO 复用。
- **HS USB(高速)**: 独立专用脚(USB_HS_DP / USB_HS_DM),预编译库固定,源码不可改 GPIO。

## 二、开机默认 LineIn Play 改动

### 2.1 文件: app_src/main_task.c

位置: `SysVarInit()` 内, 在 `PowerOnModeGenerate()` 调用之后

```c
#ifdef CFG_APP_LINEIN_MODE_EN
	// ---- [AUX] force boot into LinePlay ----------------
	// PowerOnModeGenerate() 会把 Idle 置为 ModeStateInit,
	// 这里再复位一次, 让 SysModeInit 同时 Init Idle 和 LinePlay
	SetSysModeState(ModeIdle, ModeStateReady);
	SetSysModeState(ModeBtAudioPlay, ModeStateReady);
	SetSysModeState(ModeLineAudioPlay, ModeStateInit);
	mainAppCt.SysCurrentMode = ModeLineAudioPlay;
	mainAppCt.SysPrevMode = ModeLineAudioPlay;
	APP_DBG("!!!!!!!!!!force power on mode LinePlay!!!!!!!!!!\n");
#endif
```

- **作用**: 开机强制进入 LineIn 播放模式(覆盖默认 BT 模式),受 `CFG_APP_LINEIN_MODE_EN` 宏控制。
- **恢复默认**: 删除/注释该 `#ifdef... #endif` 块即可回到默认开机模式。
- **状态修正(2026-09-30)**: 这段代码曾一度被放在 `#ifdef CFG_FUNC_BREAKPOINT_EN` 的 `#else` 分支内, 而 `CFG_FUNC_BREAKPOINT_EN` 在 `app_config.h` 中是打开的, 整段被预处理掉, 因此 **"开机强制 LineIn" 实际不生效**, 开机模式由断点记忆(或 SDK 默认 BT)决定。现已移出到 `#endif` 之后, 详见 **第八章**。

## 五、USB 升级日志 → SDK 代码映射

升级日志文件: err_logs\USB_FS.txt(IAPBurner + FS-USB-CDC 双区升级成功实录)

### 5.1 结论:走了 SDK 标准 USB-FS 双区(dual-bank)升级

- 通道: 日志 `upgrade with a channel 200` = `0x200` = `CHN_MASK_USBCDC_FS = (1<<9)`(upgrade.h L114)。
- 状态机: FlashbootState `0x4`(Apply)→`0x6`(Done),即升级请求→升级完成。
- flash_data 为预编译 ROM/flashboot 代码(flash_boot.c 内 `flash_data[0x10000]` 二进制块, v5.5.0),升级落盘/CRC 在其内部完成,APP 不可改源码。

### 8.1 问题一: 暂停大电流声 —— 第 1 版方案为何无效

先厘清 SDK 里几套静音机制的真实行为(依据为源码与反汇编):

| 接口 | 实际行为 | 渐变 |
|------|----------|------|
| `HardWareMuteOrUnMute()` (audio_vol.c) | **翻转** `mainAppCt.gSysVol.MuteFlag`, 再 `AudioDAC_SoftMute(DAC_SEL, MuteFlag, MuteFlag)` | 有 |
| `AudioDAC_DigitalMute(m,L,R)` | 写 DAC 静音位(DAC0 = 0x40014_20 bit0=L / bit1=R), **不等渐变完成即返回** | 芯片内部有, 软件不等 |
| `AudioDAC_SoftMute(m,L,R)` | 写**同一寄存器的同一批位**, 再**轮询** bit12/13(渐变完成)才返回, 10 tick 超时 | 同上 + 等待 |
| `AudioCoreSourceMute/Unmute(Index,..)` | **只置/清** `LeftMuteFlag`/`RightMuteFlag`, 零渐变 | 无 |
| `AudioCoreSourceMuteApply/SinkMuteApply` | 真正做渐变, 但 `LeftVolStep = 4096/SOURCEFRAME` -> **渐变只有 1 个音频帧**(48k/128 约 2.7ms) | 有但极短 |

由此得到第 1 版方案的三个缺陷:

1. **叠加了三层静音, 且存在硬置零旁路**  `AudioCoreSourceMuteApply()` 的分支:

   ```c
   if((!InitFlag) || (Net != FlowNet) || (mute == MuteFlagbk)) {
       if(... && (mainAppCt.gSysVol.MuteFlag || LeftMuteFlag))
           memset(PcmInBuf, 0, ...);   // 硬置零, 在随机相位砍断波形
       MuteFlagbk = mute; continue;
   }
   ```

   其中 `mute = LeftMuteFlag || RightMuteFlag || mainAppCt.gSysVol.MuteFlag`; 第 1 版一次改了其中三个,
   任何组合使 `mute` 与上一帧相等(暂停后的每一帧都成立)就落进 `memset` 硬置零 -> 爆音。Sink 侧同理。
2. **`MuteFlag` 不是本模块私有变量**: 全工程 50 余处 `HardWareMuteOrUnMute()` 会 **toggle** 它
   (音量键 audio_vol.c、切音效 audio_effect_parambin.c、提示音 remind_sound.c、模式切换 mode_task.c、各 mode deinit 等)。
   暂停后按一下音量键 -> MuteFlag 翻回 FALSE 且 `AudioDAC_SoftMute(DAC0,0,0)` -> 暂停被解除, 且状态发生跳变。
3. **DAC0 硬静音位有两个主人**: `headphone.c` 的 `HpDacOutput()` 也写 `AudioDAC_DigitalMute(DAC0_MODULE,..)`;
   第 1 版暂停时置 1、恢复时清 0, 会覆盖耳机模块的静音意图, 且硬静音在任意相位产生 **DC 阶跃**
   (DAC0 为差分输出, 送 HT97180) -> 大电流声。

### 8.2 问题二: 开机偶尔进入蓝牙

**根因: "开机强制 LineIn" 那段代码从未被编译进固件。**

- `app_config.h` 中 `#define CFG_FUNC_BREAKPOINT_EN` 是打开的;
- 该段原先位于 `main_task.c` 中 `#ifdef CFG_FUNC_BREAKPOINT_EN ... #else ... #endif` 的 **`#else` 分支内**, 整段被预处理掉;
- 于是 `PowerOnModeGenerate(pBpSysInfo)` 用**断点记忆**决定开机模式: `Mode = pBpSysInfo->CurModuleId`(NVM/Flash 保存的上次模式);
- 无记忆(或 NVM 空/损坏)时回落到 `SysMode[]` 里**第一个 `ModeStateInit`** 表项, 而 `mode_parameter.h` 中唯一初值为 `ModeStateInit` 的正是 **`ModeBtAudioPlay`**;
  `breakpoint.c` 的出厂默认 `sInitSysInfo.CurModuleId` 也是 `ModeBtAudioPlay`;
- `device_detect.c` 保存 `CurModuleId = GetSystemMode()`, 且开了 `BP_PART_SAVE_TO_NVM` + `BP_SAVE_TO_FLASH`, 即**上次模式被持久化**;
- 另外 `main_task.c` 中 `SoftFlagGet(SoftFlagUpgradeOK)` 为真时会**强制** `CurModuleId = ModeBtAudioPlay`, 即**刷完固件第一次开机必进 BT**。

所以"有时进 BT" = 上次模式是 BT(或出厂默认 / NVM 异常 / 刚升级), 与强制 LineIn 无关。

> 状态: **分析中, 尚未根治**。已定位为"两个独立机制叠加", 二者都不在暂停/静音逻辑上。

### 9.0 前提: 当前生效的暂停逻辑

`linein_mode.c` 的 `MSG_PLAY_PAUSE` 分支在 **2026-09-30 17:32** 被**有意恢复为原逻辑**(开发者确认):

- 当前生效的是 `HardWareMuteOrUnMute();`(内部 toggle `mainAppCt.gSysVol.MuteFlag`, 见 audio_vol.c:176-209);
- 第九节的方案三是在此基础上新增的。

### 9.1 现象

音源 = 电脑耳机口**直接**接入 LineIn, 调整电脑音量后:

1. 先"**嗒**"一声;
2. 紧接着**很强的"电流声"**(刺耳、宽带);
3. 随后才听到 Windows 音量变化的提示音(说明通路本身延迟很小);
4. 该噪声**慢慢衰减约几秒**;
5. 以"**嗒**"一声结束;
6. **但并未完全结束** -- 之后**每隔几秒又"嗒"一声**;
7. 再过一段时间才彻底消失, **只剩基本底噪**。

其它关键特征:

| 观察 | 指向 |
|------|------|
| 耳机与音箱**两个输出都有** | 问题在混音点之前(音源这一路), 不是某一路输出 |
| **能听到正常音乐**, 噪声叠在上面 | 输入通路是通的, 不是悬空/错接引脚 |
| 音源无信号时**只有正常底噪** | 噪声由**信号**激发, 不是持续自激 |
| **蓝牙模式不会出现** | 差异不在效果图(见 9.2), 而在送进效果图的信号 |
| "电流声"**随音源电平升高而出现** | 强烈指向**模拟输入级削顶(clipping)** |

### 9.2 关键判别: 蓝牙与 LineIn 用的是同一张效果图

启动日志一字不差(括号内为日志文件):

```text
LineIn  SysModeInit-----SysPrevMode = LinePlay SysCurrentMode = LinePlay-----
        flow:Karaoke,mode:0,memory_size:114942        (err_logs/eight.txt 等)
BT      SysModeInit-----SysPrevMode = Idle SysCurrentMode = BtPlay-----
        flow:Karaoke,mode:0,memory_size:114942        (err_logs/thr.txt)
```

该打印来自 `AudioEffect_Parambin_Init()`(audio_effect_parambin.c:528), 两种模式都会执行; `effect_flow_index` 来自断点记忆(本机为 0 = Karaoke), **不存在"按模式换图"**。

所以差异只可能在**送给这张图的信号**:

| 对比项 | 蓝牙 | LineIn |
|--------|------|--------|
| 信号来源 | A2DP 解码的**数字 PCM** | **模拟输入 -> ADC** |
| 会不会削顶 | 电平有 0 dBFS 上限, 不会 | PGA 约 0 dB 无余量, 音源满幅可顶到 ADC 满刻度以上 -> 会 |
| "没有音乐"时送进图里的是什么 | 精确的**数字 0**(源被 mute/disable) | **ADC 仍在采样** -> 连续的**低电平模拟底噪**, **永远不是 0** |

第三行是"隔几秒又嗒"的关键: 对**阈值型动态处理**来说, "精确 0"状态稳定; 而"连续低电平噪声"会**在阈值附近反复穿越 -> 反复开合 -> 每次开合一声"嗒"**。

### 9.4 LineIn 输入接口梳理(避免误读)

**结论: 当前只用 B18/B19; AUX0/B20/B21 一路都没被使能。** 三处"看起来两路都写了"的代码造成误读:

| # | 位置 | 形态 | 实际行为 |
|---|------|------|----------|
| 1 | linein_mode.c:177-193 | `#if AUX1 ... #elif AUX0 ...` | 只编译 AUX1 一支, 只把 B18/B19 设成 GPIO 并关 IE/OE; B20/B21 段**不参与编译** |
| 2 | linein_mode.c:327-335 | 同样 `#if/#elif` | 只清 B18/B19 的 `ANA_EN` |
| 3 | ctrlvars.c:871-874 | 对 AUX0 与 AUX1 **都写 PGA 增益** | 只写增益寄存器, **不等于使能输入**(误读主因) |
| 4 | ctrlvars.c:778-808 | `AudioLineChannelSet` 两个并列 `if` | 本配置下**整段 ADC1 代码被编译掉**(`#if ... MIC_ADC_SEL == ADC1_MODULE`, 而本芯片 `MIC_INPUT_CHANNEL = MIC0` -> `MIC_ADC_SEL = ADC0_MODULE`), 传 AUX1 时**函数什么都不做** |
| 5 | adc_interface.c:193-208 | `AudioADC_AnaInit` | **权威路径**: 先 `PGASel(ADC_NONE)` 把左右全部去选, 再只选 `HwCt.AUDIOADC_Ana*.INPUT` -> **只选 B18/B19** |

真正决定走哪一路的是 `HwCt.AUDIOADC_AnaLeft/Right.INPUT = ADC1_AUX1L_B18 / ADC1_AUX1R_B19`(linein_mode.c:166-171), PGA 也在那里设置: `31 - LINEIN_LEFT_GAIN_VAR`。

> 隐患: `AudioLineChannelSet()` 目前是**死函数**。若将来把 MIC 改到 ADC1(`MIC_INPUT_CHANNEL = MIC1`), 它会**突然复活**, 且 `MIC_ADC_SEL` 同步改变, 行为会整体变化。

### 9.5 根因分析(两个机制叠加)

1. **输入级削顶 -> "电流声"**
   PGA 实际约 0 dB(audio_adc.h:30-65 的 PGA 表: Vol 9 = -0.82 dB), **没有衰减余量**; 电脑耳机口满幅可达 1~2 Vrms, 足以把 ADC 打满 -> 宽带高频失真。安静段落数据接近 0, 不削顶, 所以只听到正常底噪。

2. **效果图里的阈值型动态处理 -> 把失真"拖长 + 切碎"**
   削顶产物进入 `Karaoke` 图后, 被 DRC(较长 release)、噪声门/扩展器、混响尾巴加工: 幅度被拖成几秒的衰减, 门在衰减尾巴上反复开合 -> **隔几秒一声"嗒"**。

> 注意: 该归因目前基于"现象 + 配置审计", **尚未用单变量实验证实**(实验见 9.8)。

### 9.6 效果图内相关节点(取自 audio_effect.bin 的文本导出)

导出文件: `audioeffect_res/audio_effect_for_read/audio_effect.txt`(Graph1 `Karaoke`)。

| 节点 | 关键参数 | 影响 |
|------|----------|------|
| `noise_suppressor_expander0` | enable=1, threshold=-6800, ratio=2, attack=2, release=200 | 噪声门/向下扩展器, 在衰减尾巴上反复开合 -> **"隔几秒的嗒"** |
| `drc_sc0` | enable=1, threshold_3=-4000, ratio_3=4, attack_3=10, release_3=1500 | 较长 release -> 把失真拖成"**几秒衰减**" |
| `silence_detector_music` / `silence_detector_mic` | enable=1, PCM amplitude=0 | 输入变全 0 时翻转, 也会产生咔嗒 |
| `reverb_plate_me0` | enable=1, decay=50, wetdrymix=80, predelay=40 | 混响尾巴 |
| `echo0` | enable=1, delay=256, max delay=400, attenuation=-60 | 约 5.8 ms, **不是几秒回声** |
| `pcm_delay0` | enable=0, delay=1764 | 未启用 |
| `music_gain` | enable=1, gain=-1200 | 音乐通路被压 **-12 dB** -> 迫使音源开大 -> 更容易削顶 |

档位信息: `Total Effect Mode: Bypass, ECHO, REVERB, ECHO_REVERB`; 当前 `mode:0` 即第一个(Bypass), 故 ECHO/REVERB 档位未启用(它们主要是 mic 侧档位)。

**App 层调不了这些**: `CFG_FUNC_MIC_ECHO_REVERB_EN` 在 app_config.h:151 是**注释掉的** -> `AudioEchoReverbAjust()` 函数体为空 -> `ReverbStep` 无效(见 audio_vol.c:554-572)。

### 9.7 解决方案

#### 方案一: 输入侧降压(首选, 针对"电流声")

1. **不改代码先验证**: 电脑系统音量降到 30% 左右, 用播放器音量控响度;
2. **硬件**: LineIn 输入端加分压衰减 + RC 低通; 换用真正的 Line-Out 音源(耳机口输出阻抗低、满幅电平高, 直连 LineIn 容易过载);
3. **代码(一处 2 行)**: `app_src/components/audio/ctrlvars.c:516-517`

```c
gCtrlVars.HwCt.ADC1PGACt.AUX1L_B18_Gain = 22;   /* Vol 9  约 0 dB   <- 现在 */
gCtrlVars.HwCt.ADC1PGACt.AUX1R_B19_Gain = 22;
```

注意方向: `Vol = 31 - 该值`, **数字减小 = 增益降低**。

| 设置值 | Vol | LineIn/AUX 增益 |
|--------|-----|-----------------|
| 22(现在) | 9 | -0.82 dB |
| 20 | 11 | -4.85 dB |
| **18(建议先试)** | 13 | **-8.87 dB** |
| 16 | 15 | -12.88 dB(该通路最小) |

降下来的响度在后端(数字音量/功放)补回。

#### 方案二: 效果图侧(处理"长尾巴 + 咔嗒")

必须在 **ACPWorkbench** 里修改 `audioeffect_res/audio_effect.bin` 并重新生成/刷入(源码无法修改):

- `noise_suppressor_expander0`: `enable = 0`(首选), 或把 threshold 降得更低;
- `silence_detector_music` / `silence_detector_mic`: 不需要则 `enable = 0`;
- `drc_sc0`: 缩短 `release_3`(1500 -> 200~300);
- `reverb_plate_me0`: `decay 50 -> 20`, `wetdrymix 80 -> 40`;
- 或更彻底: **新增一张"纯音乐"效果图**(不含 echo/reverb/DRC/门), 让 LineIn/AUX 走它, 由 `effect_flow_index` 切换。

#### 方案三: 暂停延后静音(已实施, 仅"错开时间", 不消除爆音)

- 文件: `app_src/app_mode_linein/linein_mode.c`
- 新增宏(第 37 行):

```c
#define LINEIN_PAUSE_MUTE_DELAY_MS		20	//[MOD_20260930-C] 暂停时延后静音的时长(ms): 须为1ms整数倍(tick=1ms), 建议<=30
```

- 暂停分支(第 219-225 行)在 `HardWareMuteOrUnMute();` **之前**插入:

```c
if(IsAudioPlayerMute() == FALSE)
{
    osTaskDelay(LINEIN_PAUSE_MUTE_DELAY_MS);
}
```

- 设计要点:
  - `HardWareMuteOrUnMute()` 是 **toggle**(audio_vol.c:176-209), 一次同时管暂停与恢复; 用 `IsAudioPlayerMute()`(读 `MuteFlag`, audio_vol.c:211-214)判断方向 -> **只延后"暂停(静音)"方向**, "恢复"方向不延后(否则会出现先静一小段才出声);
  - 必须用 **`osTaskDelay`**(任务上下文, 挂起任务并让出 CPU); **不可用 `DelayMs`**(忙等会占住 MainApp 任务, 期间不处理任何消息, 且空转抬高 CPU 占用);
  - `osTaskDelay(Cnt)` 内部为 `vTaskDelay(pdMS_TO_TICKS(Cnt))`, **Cnt 单位是毫秒**; tick = 1 ms(`OSTICK_RELOAD = 1000`, module_config.h:797; `TickRateHz`, main.c:62) -> **最小粒度 1 ms**, `osTaskDelay(0)` 只让出 CPU 不延时;
  - **它是"睡过去", 不是"淡出"**: 这 20 ms 内音频照常出声(DMA/中断在跑), 效果仅为"按暂停后多响约 20 ms 才静音", **不消除爆音**;
  - `LineInPlayRun` 运行在 **MainApp 任务**的消息循环中(mode_task.c:933), 属任务上下文, 因此 RTOS 阻塞 API 合法。

- 校验(2026-09-30): GB2312 往返无损、无 BOM、U+FFFD=0、`{}` 34/34、`#if/#endif` 与改前一致、逐行比对**仅新增 8 行**; 备份 `.dsh_scratch/linein_mode.c.before-delay.bak`。

# 十、OXS协议、USB-HID日志与GC1808输入（2026-10-09）

## 10.2 USB-HID日志

- 复用 `retarget.c` 的4 KB `usb_fifo`和现有HID `GetReport`；返回包为 `A5 5A 30 01 + 252字节`。

## 10.3 OXS协议与输出状态

- UART1 ISR仅把字节写入256字节环形缓冲；主任务解析最大64字节包、100 ms残帧超时、小端CRC-16/IBM/ARC。
- 线上帧头为 `4F 52 45 50`，实现设备信息、扬声器/耳机独立音量与静音、耳机插拔主动上报及错误ACK。

- 扬声器1~100映射1~16级；耳机1~100映射-72.2~0 dB；音量0只强制实际静音，不改显式静音标志。

## 10.4 GC1808-I2S2

- PA20由I2S1 MCLK1_OUT输出12.288 MHz；GC1808以MD0=1、MD1=1、FMT=0作I2S主机，向PA16/PA17/PA18输出3.072 MHz BCLK、48 kHz LRCLK和24-bit I2S数据。
- DSP I2S2配置为从机、RX-only、单线双声道、标准I2S、低24位有效；先开MCLK，等待100 ms后启动I2S2 RX并挂到原LineIn source。
- 音效网络非48 kHz时仅使用AudioCore `SRC_ONLY`，不开启全局I2S2 mix source，不启用DPLL跟踪。

## 10.5 验证状态

- Windows主机GCC已对GC1808和内部ADC两个分支执行语法/预处理检查，涉及源文件无错。
- AndeSight随附旧Cygwin/nds32命令行工具在当前Windows环境因系统DLL重定位错误无法启动；需在AndeSight GUI内执行最终完整编译和板级验证。

## 10.6 USB接入后误切声卡及通用HID工具无日志修正

- 现象：连接PA8/PA9到电脑后先播“线路模式”，随后播“声卡模式”，LineIn/GC1808通路被释放，耳机和喇叭均无外部音源声音。
- 原因：`CFG_APP_USB_AUDIO_MODE_EN`、`CFG_APP_USB_FS_AUDIO_MODE_EN`仍使USB插入事件进入声卡应用模式。
- 修正：关闭HS/FS声卡应用模式，只保留 `CFG_COMMUNICATION_BY_FS_USB`。FS设备插入时直接初始化 `FS_HID`，不再发送可切换到声卡模式的有效模式映射。
- 原HID日志仅响应控制传输Input `GetReport`，且数据HID接口没有中断IN端点；WebHID及常见通用HID工具只监听中断IN，因此无法显示日志。
- 在不改VID/PID、不占用原接口0的前提下，新增接口1和EP5 IN（全速64字节）作为通用日志通道。每包为 `A5 5A 30 01 + 最多60字节日志 + 零填充`。
- 原接口0的256字节控制 `GetReport`、在线调音和Feature Report升级触发保持不变；两种日志读取方式共用4 KB FIFO，发送失败不推进读指针。

## 11.2 RL协议当前实现和联调结果

## 11.3 双功放和新调音参数

- 重新启用两颗ACM8625S：TWE全频功放地址`0x58`，WF低音功放地址`0x5A`，两者共用DSP的I2S1输出，但各自下载独立寄存器参数。

## 11.4 完全断电后I2S时钟异常的现象和判断

- 历史现象是烧录或软件复位后可能正常，但完全断电再上电后出现错误频率。曾测得GC1808 MCLK约24.57 MHz、BCLK约6.16 MHz，扬声器侧BCLK/LRCLK也偏离48 kHz系统目标。
- 目标频率应为：PA20 MCLK 12.288 MHz；GC1808输出BCLK 3.072 MHz、LRCLK 48 kHz；扬声器I2S1输出BCLK 3.072 MHz、LRCLK 48 kHz。
- PA20是`MCLK1_OUT`，其时钟硬件属于I2S1模块。因此`Gc1808MclkStart()`使用`I2S1_MODULE`是正确设计，不能因为GC1808数据进入I2S2就改成`I2S2_MODULE`。
- LineIn启动时，`ModeCommonInit()`先初始化扬声器I2S1；随后GC1808路径调用`AudioI2S_Init(I2S2_MODULE, ...)`。该公共接口即使配置的是I2S2从机，也会重新写入四路音频PLL并立即打开I2S2 RX/DMA。
- 冷启动时公共PLL重新配置发生在原MCLK设置之后，I2S1分频和MCLK输出不再是最后写入的稳定状态；同时I2S2会在GC1808时钟尚未重新稳定时开始接收。这一初始化顺序是本次修正的主要对象。

## 11.5 冷启动时钟修正内容

- `Gc1808MclkStart()`首先显式把PLL2重新锁定为24.576 MHz，然后配置I2S1 MCLK源、二分频和48 kHz时序，使PA20最终输出12.288 MHz。
- 启动顺序调整为：准备I2S2参数并调用`AudioI2S_Init()`；立即关闭I2S2 RX和DMA并清空环形FIFO；重新应用I2S1/PLL2最终时钟；等待100 ms；再次清空FIFO；最后依次启用DMA、I2S2 RX、I2S2模块和LineIn AudioCore source。
- 原有100 ms等待只改变位置，没有额外增加启动延迟。等待从“可能被后续PLL配置覆盖的MCLK”之后移动到“最终MCLK配置”之后，能够覆盖GC1808手册要求的初始化周期。
- 在打开AudioCore source前增加一次性启动诊断日志，记录I2S1时钟源、MCLK分频、I2S1采样率和I2S2采样率。该日志发生在UART1协议接管前，不会形成周期输出或污染协议阶段。
- LineIn退出时继续调用`Gc1808MclkStart()`保持PA20 MCLK，避免模式通路重建期间GC1808因失去MCLK进入掉电复位。
- 内部ADC编译分支未改变；GC1808仍为I2S2从机RX后端，不启用全局I2S2混音源，也不增加DPLL跟踪。

## 11.6 验证要求和当前状态

- 本次已完成源码静态检查、CP936/换行检查、AndeSight编译、烧录及首轮示波器验证。
- 2026-10-12板级实测：GC1808 MCLK平均约12.2x MHz（标称12.288 MHz）、LRCLK 48 kHz、BCLK 3.072 MHz；功放I2S1 LRCLK约48 kHz、BCLK约3.072 MHz。
- 首轮结果表明两侧均恢复为48 kHz、每帧64 BCK，公共PLL和I2S1二分频修正已生效；MCLK的12.2x MHz读数处于示波器显示和测量误差范围内。
- 编译时确认GC1808和内部ADC两个宏分支均无未定义符号，且`new_amp_parameter/`不再出现在编译日志中。
- 烧录后至少执行5次“完全断电、等待电源放电、重新上电”，不能只做下载器复位或软件重启。
- 每次冷启动测量PA20、PA16、PA17及扬声器I2S1 BCLK/LRCLK，并记录是否始终得到12.288 MHz、3.072 MHz和48 kHz。

## 12.4 开机恢复优先级

5. `RL_OutputControlRefresh()`把最终状态应用到两颗扬声器功放和耳机输出。

# 十三、AD_EN 20 kHz PWM同步阻抗检测与当前验证（2026-10-14）

本节记录把耳机阻抗检测激励从PB8/AD_EN持续直流高电平改为短时PWM，并在固定PWM相位同步采集ADC的实现。目标是在保留16/32 ohm判定和RL主动上报的同时，缩短AD_EN激励时间，降低耳机中可听见的插拔冲击声。

## 13.1 配置与硬件资源

- 在`app_src/system_config/app_config.h`第96行新增并默认开启`CFG_HP_IMPEDANCE_PWM_SYNC_EN`。定义该宏时使用PWM同步检测；注释后保留原直流AD_EN、8次采样、去除最大最小值后求平均的旧实现，便于A/B对比和回退。
- PB8仍为AD_EN输出，但检测期间复用成`TIMER7_PWM2_A16_B8`；Timer7/PWM2输出20 kHz、50%占空比。采样结束、配置失败、ADC失败或任务超时后都会解除PWM复用并强制PB8恢复GPIO低电平。
- Timer7的PWM0和PWM3比较点只作为ADC同步采样时刻，不映射到外部引脚。PWM0位于周期40%，用于高电平采样；PWM3位于周期90%，用于低电平采样。
- ADC仍使用PA30/ADC0采右声道、PA31/ADC1采左声道，并继续使用`SarADCMutex`避免与其他SAR ADC使用者并发冲突。
- `Timer7_Interrupt`原先只有启动文件中的弱默认处理函数，当前由耳机模块提供实际实现。Timer7因此成为耳机阻抗检测专用资源，后续增加定时器功能时必须先检查冲突。

## 13.2 PWM采样流程

- 参数集中在`app_src/components/headphone/headphone.c`第63行及第76至100行：阻抗分界240 mV、插入稳定等待1000 ms、左右异常差300 mV、PWM 20 kHz、占空比50%、高低采样相位40%/90%、1个预热周期、2个有效周期和5 ms任务超时。
- 一次检测脉冲串总共3个PWM周期：第1周期预热，第2周期采右声道，第3周期采左声道。20 kHz下理论总激励时间约150 us。
- `Timer7_Interrupt()`位于`headphone.c`第303至355行。在每个有效周期的40%时刻取得高电平值，在90%时刻取得低电平值。
- `HpPwmSampleBurst()`位于第418至491行。阻抗判定使用`高电平ADC值 - 低电平ADC值`，再按`差值 * 3300 / 4096`换算为毫伏。`HP_IMPEDANCE_INFO`中的`right_adc/left_adc`在PWM模式下保存差值，不再是直流绝对ADC值。
- 有效性检查包括：中断已经完成、ADC没有超时、采样没有达到`0x0FFF`饱和、左右声道均为高电平值大于低电平值。失败时本次结果保持未知。
- 插入处理位于`HeadphoneTaskPoll()`第1112至1257行。去抖后等待1000 ms，再执行PWM检测。ADC无效、首次左右分类不同或左右差值超过300 mV时，等待10 ms后最多重测一次。
- 第二次测量结束后不再进行第三次重测。最终结果保存到`s_imp`，再恢复耳机输出并主动上报插入事件。

## 13.3 阻抗判定和RL上报

- `HpImpJudge()`位于`headphone.c`第495至500行：差分电压小于240 mV判为16 ohm，大于等于240 mV判为32 ohm。
- `RL_HeadphoneImpedanceGet()`位于第660至668行。仅当左右同时为16 ohm或同时为32 ohm时返回有效阻抗；采样无效或左右不一致时返回32位有符号数`-1`。
- `RL_SendHeadphoneEvent()`位于第670至690行。插入主动事件使用命令`0x10`，4字节小端载荷分别为：16 ohm=`10 00 00 00`、32 ohm=`20 00 00 00`、无效=`FF FF FF FF`；拔出事件使用命令`0x11`且无载荷。
- 串口文本日志会把原始`FF`显示或保存成`EF BF BD`替换字符。协议判断应以HEX原始字节为准，不应把替换字符误认为设备真实发送内容。

## 13.4 当前串口和听感结果

- 已通过COM9、115200和串口工具IPC确认，插入`0x10`及拔出`0x11`主动事件均能产生，事件Packet ID按顺序递增，重新上电后从1开始。
- 当前日志缓存统计到16 ohm有效结果6次、32 ohm有效结果0次、无效`-1`结果10次；最新一组插入结果依次为`-1、16、-1、16、-1`。
- 这说明串口事件链路已经正常，但PWM阻抗识别尚未通过准确率验收。16 ohm可以识别但存在波动，32 ohm暂未出现有效上报；240 mV阈值是否适用于PWM差分值仍需依据原始ADC数据重新标定。
- 普通插拔的听感由原先两声较明显“咚咚”降低为一声较轻“嗒”。完全断电再上电仍可听到两声较轻“嗒”，但明显小于旧方案。
- 上电两声可能是首次结果异常后在10 ms处重测，也可能分别对应PWM检测和PB10/HP_EN开启、DAC0解除静音。当前串口事件只上报最终结果，无法仅靠事件帧区分是否发生重测。

## 13.5 后续诊断和参数调整要求

1. 示波器同时观察PB8/AD_EN和PB10/HP_EN。若PB8出现两个相隔约10 ms的PWM脉冲串，则可以确认发生重测；若PB8只有一个脉冲串而第二声与PB10上升沿同步，则重点处理耳放使能和DAC解除静音时序。
2. 通过`CFG_FUNC_HEADPHONE_DEBUG_LOG_EN`临时输出左右高低ADC、差分码、毫伏值和有效标志。UART1同时承载RL协议，诊断固件应暂停协议或增加专用二进制调试命令，避免文本日志污染协议。
3. 对16 ohm和32 ohm耳机各重复至少20次，统计左右差分毫伏的最小、最大和平均值，再调整`HP_IMP_SPLIT_MV`。不能继续直接假定直流方案的240 mV分界适用于PWM差分方案。
4. 若PB8高电平在25 us内未稳定，先逐级降低`HP_PWM_FREQ_HZ`，再调整40%和90%采样相位。增加预热周期虽然可能改善稳定性，但会延长激励并增加可闻冲击风险。
5. `HP_PWM_VALID_CYCLES`当前与“右声道1周期、左声道1周期”的数组和索引逻辑绑定，不能只修改宏值。若要多周期平均，必须同时修改`Timer7_Interrupt()`声道分配和`HpPwmSampleBurst()`汇总算法。

更完整的代码路径、参数表、修改注意事项和测试清单见`docs/AD_EN_PWM同步阻抗检测设计与维护指南.md`。

## 13.6 50 kHz单周期采样实验调整

- 当前硬件已将PB8的AD_EN直接连接到AD_OUT，不再经过原理图中的三极管和MOS开关。示波器测量AD_EN/AD_OUT等同于直接观察PB8输出，因此不能再用MOS开关或后级RC响应解释毫秒级脉宽。
- `HP_PWM_FREQ_HZ`已经由20 kHz调整为50 kHz，50%占空比下理论周期为20 us，高电平为10 us。
- 板级初测只能观察到一个约4 ms高电平，未观察到预期的50 kHz周期。该时长接近`HP_PWM_TASK_TIMEOUT_MS=5 ms`，初步怀疑Timer7比较中断未按预期完成，最终由任务超时路径关闭PWM。该问题仍需通过PB8单次触发波形和中断计数继续确认。
- 为缩短检测激励，代码由“1个预热周期、右声道1周期、左声道1周期”改成单个PWM周期。`HP_PWM_TOTAL_CYCLES=1`，`HP_PWM_SAMPLE_CHANNELS=2`。
- `Timer7_Interrupt()`现在在40%比较点依次采右、左高电平，在90%比较点依次采右、左低电平，随后立即停止PWM。`HpPwmSampleBurst()`仍使用两个声道各自的高低ADC差值进行毫伏换算和阻抗判断，RL上报接口不变。
- 50 kHz下40%到90%之间只有10 us，需要完成两次阻塞式ADC转换。这是实验性配置；如果ADC转换时间超过窗口，低电平采样可能延迟或跨周期，必须结合示波器和原始ADC值判断，不能只依据能否编译确认时序有效。
- 已使用AndeSight RDS v323的nds32le工具链单独编译`app_src/components/headphone/headphone.o`，编译成功，无警告和错误。源文件继续保持CP936兼容编码和LF换行。
- 如果烧录后仍为约4至5 ms单高电平，说明问题不是三周期数量导致，应优先检查`Timer7_Interrupt()`是否进入、比较标志是否产生以及`s_hpPwmSample.done`是否在超时前置位。
